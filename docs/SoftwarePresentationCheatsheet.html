TOPIC 01

QR Code Detection Pipeline

One-line summary: The OAK-D Lite's Myriad X VPU finds the QR region in the full image and sends only a tiny greyscale crop to the Jetson, which runs ZBar C++ to decode it. The Jetson never processes a full camera frame.

The key architectural insight — say this if asked why we split QR decode across two chips: Running ZBar on a full 4K frame at 60 fps on the Jetson would consume the entire CPU budget. By having the Myriad X VPU crop out just the likely QR region first (typically 200×200 px), ZBar decodes a tiny image in under 1 ms. This is the only way to stay inside the 30 ms FSM cycle. 
/**
 * QR DETECTION LOOP
 * 
 * Architecture: two-stage decode
 *   Stage 1: Myriad X VPU (inside OAK-D Lite)
 *            → scans full RGB frame
 *            → finds highest-contrast rectangle (likely a QR)
 *            → crops it to greyscale ROI (tiny image)
 *            → sends to Jetson via USB 3.0
 *
 *   Stage 2: Jetson TX2 NX CPU
 *            → receives small greyscale crop
 *            → runs ZBar C++ plugin (fast: small image)
 *            → stores decoded string as target_id
 *
 * Why this split?
 *   ZBar on full 4K @ 60fps on the Jetson = ~20ms/frame = budget blown.
 *   ZBar on a 200x200 crop               = ~0.5ms/frame = trivial.
 *   The Myriad X does the hard spatial search for free (dedicated NPU).
 *
 * This function runs inside the 30ms FSM cycle.
 * The drone HOLDS POSITION at 5m until target_id is confirmed.
 */

string target_id = "";    // Will be set when QR is decoded. Empty = gate not passed.
int    fail_count = 0;    // Counts consecutive frames where ZBar finds nothing.

for (/* each camera frame from OAK-D pipeline */) {

    // Step 1: Myriad X has already done the heavy lifting.
    // get_qr_crop() returns the pre-cropped greyscale ROI from the VPU.
    // This is NOT the full image — it is a small rectangle around
    // the highest-contrast region the VPU detected.
    auto roi = myriad_x.get_qr_crop();

    // Step 2: ZBar decodes the tiny crop.
    // Fast because the input is small.
    // zbar.scan() returns the decoded string if a valid QR is found,
    // or an empty string if not.
    string decoded = zbar.scan(roi);

    if (!decoded.empty()) {
        target_id  = decoded;            // Mission gate passed. Store the target.
        fail_count = 0;
        transition_to(PHASE_BANNER_DETECT);   // Proceed to find corridor entrance.

    } else {
        fail_count++;
        // If we have missed 8 consecutive frames (~130ms at 60fps),
        // the OAK-D Lite view of the QR is probably blocked or angled.
        // Switch to Arducam B0251 which faces straight down via CSI
        // giving a near-nadir view from 5m altitude. This is much easier
        // to decode than a tilted view.
        if (fail_count >= 8)
            switch_camera(ARDUCAM_CSI);   // CSI port confirmed on TX2 NX carrier.
    }
}
// Drone stays hovering at 5m until target_id is set.
// No timeout — 15-minute mission clock is the only limit.
Why doesn't the Jetson just decode the QR directly from the full camera stream?
Because ZBar on a 4K frame at 60fps would take ~20ms per frame, which is the entire FSM cycle budget. By having the Myriad X find and crop the QR region first, ZBar only processes a ~200×200 pixel image — about 0.5ms. The Myriad X does the spatial search for free on its dedicated NPU.
What if the QR code is at an angle or partially obscured?
After 8 consecutive failed frames (~130ms), we switch to the Arducam B0251. This camera faces straight down (10° tilt) via CSI port on the TX2 NX carrier board. At 5m altitude directly above the QR, this gives a near-nadir view which ZBar decodes much more reliably than a tilted OAK-D view.
What does "ZBar C++" mean? Isn't there a Python library?
ZBar is a C library. We run it as a native C plugin inside GStreamer — not through Python bindings. There is zero Python in the flight path. Everything is C++. Python would add interpreter overhead and GIL issues that are unacceptable in a real-time loop.
TOPIC 02

Corridor Navigation — Forward Lap

Most likely judge question — memorise this answer: "Why doesn't the forward lap use obstacle avoidance?" Answer: The competition rules (confirmed by our team contact) state there are NO physical obstacles in the forward-lap corridor. Running A-star and Visual SLAM on the forward lap would waste 15–25ms of our 30ms budget for nothing. We save the full pipeline for the return lap where obstacles are actually present.

The forward lap uses depth-centring: sample the depth map at left and right column regions, compute the asymmetry, and send a proportional lateral velocity correction to keep the drone equidistant from both walls.

/**
 * FORWARD LAP — Corridor Wall-Following
 *
 * What it does:
 *   Keeps the drone centred in the 3.5m corridor by reading the
 *   depth to the left wall and the right wall each frame, then
 *   applying a lateral velocity correction proportional to the
 *   asymmetry between them.
 *
 * Why not A-star here?
 *   Forward lap has NO obstacles (confirmed). A-star path planning
 *   + Visual SLAM together take 15–25ms on the TX2 NX. Our total
 *   FSM cycle budget is 30ms. Running obstacle nav on an empty
 *   corridor would leave only 5–15ms for everything else.
 *
 * Input:  depth_map — stereo depth image from Myriad X VPU (each 30ms)
 * Output: lateral velocity command vy_cmd sent to Pixhawk via MAVLink
 */
void corridor_centre_control(const DepthFrame& depth_map) {

    // Sample median depth on the left third of the frame.
    // Median is used (not mean) to reject outlier pixels (e.g. corridor
    // entrance reflection artifacts, dust particles close to camera).
    float left_dist  = median_depth_in_region(depth_map, LEFT_COLUMN_ROI);

    // Sample median depth on the right third of the frame.
    float right_dist = median_depth_in_region(depth_map, RIGHT_COLUMN_ROI);

    // lateral_err > 0  means left wall is farther → drone drifted toward RIGHT wall
    // lateral_err < 0  means right wall is farther → drone drifted toward LEFT wall
    float lateral_err = left_dist - right_dist;

    // Proportional controller: gain -0.3 converts metres of asymmetry
    // into m/s lateral velocity.
    // Example: 0.5m asymmetry → 0.15 m/s correction ← gentle, stable.
    // The negative sign: if we drifted right (err > 0), push left (vy < 0).
    float vy_cmd = -0.3f * lateral_err;

    // Asymmetry under 0.3m = close enough to centre, no correction needed.
    // Avoids oscillation from correcting tiny random noise.
    if (std::fabsf(lateral_err) < 0.3f)
        vy_cmd = 0.0f;

    // Send velocity setpoint to Pixhawk via MAVLink.
    // FWD_SPEED = 2.0 m/s ideal (hard cap 5.0 m/s enforced at FC level).
    mavsdk.send_velocity(FWD_SPEED, vy_cmd, 0.0f);
}
What if one wall is missing — e.g. an open section of the corridor?
The depth map returns maximum range (around 15m for OAK-D Lite) for open space. If one side reads max-range, the asymmetry is large and the drone corrects toward the side that does have a wall. In practice this means the drone will hug the existing wall gently, which is the correct behaviour in an open section.
TOPIC 03

Obstacle Avoidance — Return Lap

The return lap activates the full obstacle pipeline: A-star path planning on a 2D occupancy grid derived from the Myriad X depth map, updated every 30ms. To keep the TX2 NX within its cycle budget, the computationally heavy map-fusion and A-star graph search are offloaded to the ground station over the 3DR backup telemetry link.

/**
 * RETURN LAP — Obstacle-aware navigation
 *
 * Full pipeline (vs forward lap which uses wall-follow only):
 *   1. Myriad X generates depth-segmented image each frame
 *   2. TX2 NX streams raw segments to GCS via 3DR MAVLink data msgs
 *   3. GCS fuses segments into 2D occupancy grid (SLAM / NVBlox)
 *   4. GCS runs A-star on the grid → optimal waypoint sequence
 *   5. GCS sends solved waypoints back to TX2 NX over 3DR link
 *   6. TX2 NX executes waypoints, checking for updates every 30ms
 *
 * Why offboard?
 *   Visual SLAM fusion + A-star together = 15–25ms on TX2 NX.
 *   Total FSM cycle = 30ms → leaves only 5ms for everything else.
 *   Offloading frees the onboard loop to focus on safety checks,
 *   MAVLink dispatch, and actuator commands.
 *
 * Safety zones (computed entirely onboard every frame, NOT offloaded):
 *   CLEAR  = depth > 5.0m → cruise at 2 m/s
 *   CAUTION = depth 2–5m  → slow to 1 m/s
 *   DANGER = depth < 2m OR red pixel present → full stop
 *
 * The safety zone check is onboard and fast (pure lookup per pixel).
 * It overrides the GCS-solved waypoint if a sudden obstacle appears.
 */

// Safety zone enum — evaluated every 30ms
enum SafeZone { CLEAR, CAUTION, DANGER };

/**
 * classify_zone()
 * Called once per FSM cycle (30ms) with the minimum forward depth
 * reading and a flag indicating whether any red pixel is present
 * in that region.
 *
 * Red pixel takes priority: even if the physical depth is clear,
 * a red zone marking must be treated as DANGER (we cannot fly over it).
 */
SafeZone classify_zone(float depth_m, bool red_pixel_present) {
    if (red_pixel_present)      return DANGER;   // red zone → never enter
    if (depth_m < 2.0f)        return DANGER;   // wall/obstacle very close
    if (depth_m < 5.0f)        return CAUTION;  // obstacle approaching
    return CLEAR;
}

// Speed cap per safety zone
float get_safe_speed(SafeZone z) {
    if (z == DANGER)   return 0.0f;   // full stop
    if (z == CAUTION)  return 1.0f;   // 1 m/s
    return MAX_CRUISE_SPEED;           // 2.0 m/s
}

// Main return-lap loop
while (fsm_state == RETURN_FLIGHT) {
    SafeZone z = classify_zone(
        myriad_x.get_min_forward_depth(),
        myriad_x.red_pixel_in_forward_region()
    );
    float speed = get_safe_speed(z);

    // Get next waypoint from GCS-solved grid (received over 3DR link).
    // If grid is stale (> 200ms), re-request from GCS.
    Waypoint wp = gcs_grid.next_waypoint();

    mavsdk.send_velocity(speed * wp.fwd_component,
                          speed * wp.lat_component, 0.0f);
}
What is A-star and why did you choose it?
A-star is a graph search algorithm that finds the shortest path through a grid while avoiding marked obstacles. We chose it because it is deterministic, computationally predictable, and works well on 2D occupancy grids. Unlike a neural network-based planner, A-star always finds the optimal path if one exists, and its worst-case compute time is bounded.
What happens if the 3DR telemetry link drops mid-return-flight?
The TX2 NX has the last-received occupancy grid cached. It continues executing that path while marking the grid as stale. Simultaneously, the safety zone check (CLEAR/CAUTION/DANGER) remains fully onboard — the drone can still slow and stop based on live depth data even with no GCS connection. If the grid is stale beyond 500ms, the drone slows to 0.5 m/s and wall-follows (same as forward lap) until the link recovers.
TOPIC 04

Red Zone Avoidance

Red zone detection uses HSV colour segmentation with two hue bands (0–10° and 170–180°) because red wraps around the HSV colour wheel and appears near both 0° and 180° depending on lighting.

/**
 * RED ZONE DETECTION — HSV Colour Segmentation
 *
 * Why two hue bands?
 *   In the HSV colour model, red straddles the 0°/360° boundary.
 *   Under one lighting condition, a red object reads as hue ~5°.
 *   Under another (e.g. warmer sunlight), the same object reads as ~175°.
 *   If we only check hue 0–10°, we miss ~50% of real-world red detections.
 *   Solution: check BOTH ends of the hue spectrum and combine with OR.
 *
 * Why these saturation/value thresholds?
 *   Saturation >= 120: ensures we don't flag desaturated (pinkish/orange) surfaces.
 *   Value >= 80: ensures we don't flag dark shadow areas as red.
 *   These values were tuned for outdoor daylight conditions.
 *
 * Runs on: Myriad X VPU inside the OAK-D Lite (fast, dedicated colour pipeline)
 * Output: red_mask — binary image where 255 = red pixel confirmed
 */

// Convert frame to HSV colour space first.
// CLAHE brightness correction must be applied BEFORE this step
// (see Auto Brightness section) to ensure consistent saturation values
// across the bright delivery zone and shaded corridor.
cv::Mat hsv;
cv::cvtColor(frame_bgr, hsv, cv::COLOR_BGR2HSV);

// Band 1: Classic red (hue near 0°)
// Lower: H=0,  S=120, V=80   Upper: H=10, S=255, V=255
cv::Mat mask1;
cv::inRange(hsv, cv::Scalar(0, 120, 80),
                cv::Scalar(10, 255, 255), mask1);

// Band 2: Wrapped red (hue near 180°)
// Lower: H=170, S=120, V=80  Upper: H=180, S=255, V=255
cv::Mat mask2;
cv::inRange(hsv, cv::Scalar(170, 120, 80),
                cv::Scalar(180, 255, 255), mask2);

// Combine: a pixel is RED if it matches EITHER band.
cv::Mat red_mask;
cv::bitwise_or(mask1, mask2, red_mask);

// Integrate with depth safety map:
// Red pixel at position (y,x) → classify that depth cell as DANGER
// regardless of what the physical depth reading says there.
// This prevents the drone from trying to fly "through" a red zone
// just because it has a clear depth reading (e.g. an open floor marking).
for (int y = 0; y < depth_map.rows; y++) {
    for (int x = 0; x < depth_map.cols; x++) {
        bool is_red = (red_mask.at<uint8_t>(y, x) > 0);
        safety_map[y][x] = classify_zone(depth_map.at<float>(y, x), is_red);
    }
}
What if the lighting changes colour temperature mid-flight?
This is exactly why we use CLAHE auto brightness correction before the HSV mask runs. CLAHE adjusts local contrast without touching hue, so a red marker still reads as red even if the overall frame gets brighter or darker as the drone moves from shade into sunlight. Additionally, the dual-band detection means we catch red across both ends of the hue spectrum.
How close can the drone get to the red zone before it stops?
The safety zone system triggers DANGER as soon as a red pixel appears in the forward region of the depth map. At 2 m/s cruise speed and a 30ms FSM cycle, the drone can stop within roughly 6–10cm of the red zone boundary (reaction distance = speed × cycle time). The physical depth check at 2m is an additional safety buffer for any non-red physical obstacles near the zone edge.
TOPIC 05

Delivery Zone QR Identification

At 10m altitude, the drone scans for all QR codes in the delivery zone, matches against target_id, rejects any near the red zone, computes the 3D world position, and confirms it over 3 consecutive frames before descending.

/**
 * DELIVERY ZONE QR IDENTIFICATION — 5-step process
 *
 * Context:
 *   The drone is hovering at 10m altitude in the 40×30m delivery zone.
 *   OAK-D Lite is tilted 45°. At 10m, it sees the floor ~10m ahead
 *   (because tan(45°) × 10m = 10m horizontal offset).
 *   The drone performs a slow lateral sweep at under 1 m/s to bring
 *   multiple QR codes into the camera's field of view.
 *
 * Goal: find the ONE QR code that:
 *   (a) decodes to a string matching target_id (from the start QR gate)
 *   (b) is NOT inside or within 1.5m of the red zone
 *   (c) is confirmed at the same 3D position across 3 consecutive frames
 */

int     confirm_count = 0;
Vector3 qr_3d_pos;          // 3D world-frame position of the target QR
Vector3 last_position;

while (fsm_state == SCAN_DELIVERY_ZONE) {

    // Step 1 + 2: Myriad X finds all QR candidate regions in the RGB frame
    // and returns each as a cropped greyscale ROI.
    vector<QRCrop> crops = myriad_x.get_qr_regions();

    for (auto& crop : crops) {

        // Step 3a: Decode the crop with ZBar.
        string decoded = zbar.scan(crop.image);
        if (decoded != target_id) continue;   // Not our target — skip.

        // Step 3b: Red zone rejection.
        // Check if the bounding box centroid of this QR is within 1.5m
        // of any red pixel cluster in the current frame.
        // If yes, skip this QR even if it decodes correctly —
        // we cannot land the payload in or near the red zone.
        if (in_red_zone(crop.bbox, red_mask, 1.5f)) continue;

        // Step 4: 3D position via pinhole projection.
        //
        // We know:
        //   px, py = pixel coordinates of QR centroid
        //   depth  = stereo depth at that pixel (from Myriad X)
        //   K      = camera intrinsic matrix (focal length fx, fy; principal point cx, cy)
        //   T_world = drone pose from GPS + IMU (position + orientation)
        //
        // Formula (pinhole model):
        //   X_cam = (px - cx) * depth / fx     ← horizontal world offset
        //   Y_cam = (py - cy) * depth / fy     ← vertical world offset
        //   Z_cam = depth                      ← distance along camera axis
        //
        // Then rotate by drone orientation and translate by GPS position
        // to get the QR's absolute world-frame coordinates.
        float depth = depth_map.at(crop.centroid_y, crop.centroid_x);
        Vector3 pos = pinhole_to_world(crop.centroid, depth, K, T_world);

        // Step 5: 3-frame confirmation.
        // Require the SAME position (within 0.3m tolerance) across
        // 3 consecutive frames before committing to fly there.
        // This rejects: lens reflections, partial QR codes, sensor noise.
        if (distance(pos, last_position) < 0.3f) {
            confirm_count++;
            if (confirm_count >= 3) {
                qr_3d_pos = pos;        // LOCKED. Start descent.
                transition_to(PHASE_DELIVERY);
                break;
            }
        } else {
            confirm_count = 1;         // Reset: position jumped, restart count.
            last_position = pos;
        }
    }
}
What if two QR codes decode to the same target_id?
The rulebook guarantees each team receives a unique target. In practice, if somehow two QRs decoded the same string, we would pick the first one that also passes the red zone check and 3-frame confirmation. The physical placement of multiple identical QRs in a competition zone is practically impossible — they are printed uniquely per team.
How accurate is the 3D position from pinhole projection?
At 10m altitude, the stereo depth accuracy of the OAK-D Lite is approximately ±0.3–0.5m for a well-lit flat target. Our zone alignment PID then brings the drone to within 0.25m of the QR centroid using live visual feedback from 5m altitude, so the initial 10m estimate only needs to be accurate enough to fly to the right general location — the fine alignment is done separately during the descent.
TOPIC 06

Autonomous Payload Deployment — ADRC Winch

ADRC explained simply for judges: Traditional winch control would need a full pendulum physics model (cable length, mass, air drag). We don't have that — cable length changes with altitude and the payload mass isn't precisely calibrated. Instead, our Extended State Observer watches the IMU attitude rate every 10ms and treats any swing it detects as a "disturbance to cancel" — without ever needing to know the pendulum parameters. It estimates the disturbance, applies a counterforce, and damps the oscillation in real time. 
/**
 * ADRC WINCH CONTROL — Active Disturbance Rejection
 *
 * The Problem:
 *   When a payload hangs on a Kevlar cable at 5m altitude, it acts like
 *   a pendulum. Any horizontal wind, lateral drone movement, or vibration
 *   causes the payload to swing. If the swing grows, the cable can tangle,
 *   the payload drifts off-target, or the drone is destabilised.
 *
 * Classical solution (NOT what we use):
 *   Model the cable as a physical pendulum: derive equations of motion,
 *   know the exact cable length (L), payload mass (m), and drag coefficient.
 *   Problem: L changes with deployment height; m is uncertain; drag is unknown.
 *
 * Our solution — ADRC (Active Disturbance Rejection Control):
 *   The Extended State Observer (ESO) reads the IMU attitude rates at 100 Hz.
 *   It treats the pendulum swing as an "external disturbance" acting on the
 *   drone's attitude. It ESTIMATES the disturbance magnitude from the rate
 *   signals WITHOUT needing any physical model of the cable or payload.
 *   When the estimated disturbance exceeds the threshold, it:
 *     (a) Brakes the winch motor (stops cable from adding more energy to the swing)
 *     (b) Sends a micro attitude correction to the Pixhawk opposing the swing
 *
 * This works regardless of cable length, payload weight, or wind conditions.
 */

// ── Constants (tuned for our specific N20 + Kevlar + 100g payload) ──
const float WINCH_LOWER_DUTY    = 0.30f;  // 30% PWM on DRV8838 H-bridge for lowering
const float WINCH_RETRACT_DUTY  = 0.20f;  // 20% PWM for reel-back (less force needed)
const int   RAMP_STEPS           = 10;    // Number of incremental duty steps in ramp
const int   RAMP_INTERVAL_MS     = 50;    // Milliseconds between each ramp step
const float WOBBLE_LIMIT_DPS     = 8.0f;  // IMU rate threshold to trigger brake
const float GROUND_CONTACT_MA    = 180.0f;// DRV8838 current spike = N20 stall = ground

/**
 * Phase A: Pre-lower stabilisation gate.
 * Drone must be stable before we let the cable out.
 * If GPS is drifting (wind) or attitude is oscillating, lowering would
 * create a large pendulum swing immediately.
 */
wait_for_stable_hover(
    /*gps_drift_limit=*/0.5f,   // m/s horizontal GPS velocity
    /*rate_limit_dps=*/3.0f    // max roll/pitch rate from IMU
);

/**
 * Phase B: Soft ramp lower — never step the motor on instantly.
 * A sudden 30% duty start would jerk the cable and immediately excite
 * the pendulum. We ramp over 500ms (10 × 50ms) for a gentle start.
 * Also protects the cable attachment point from shock loads and prevents
 * cable bunching on the LW-PLA spool at high-speed starts.
 */
ramp_drv8838(from=0.0f, to=WINCH_LOWER_DUTY, steps=RAMP_STEPS, interval_ms=RAMP_INTERVAL_MS);

// Phase C: Active swing damping loop — runs while cable is lowering.
while (!ground_contact_detected) {

    float roll_rate  = imu.roll_rate_dps();
    float pitch_rate = imu.pitch_rate_dps();

    if (std::fabsf(roll_rate)  > WOBBLE_LIMIT_DPS ||
        std::fabsf(pitch_rate) > WOBBLE_LIMIT_DPS) {

        // ADRC response: stop adding energy to the swing.
        drv8838.brake();                     // Hold cable still for 300ms
        std::this_thread::sleep_for(300ms);
        drv8838.resume(WINCH_LOWER_DUTY);   // Resume lowering gently

        // Also send micro attitude correction to Pixhawk opposing the swing.
        // This physically counters the pendulum reaction force on the drone body.
        // Vector is computed from ESO's disturbance estimate direction.
        AttitudeTarget correction = eso.compute_anti_swing_correction();
        mavsdk.set_attitude_target(correction);
    }

    // Phase D: Ground contact detection.
    // N20 gear motor physically stalls when payload touches ground.
    // DRV8838 H-bridge shows current spike above GROUND_CONTACT_MA.
    // No separate sensor needed — current sensing is built into DRV8838.
    if (drv8838.current_ma() > GROUND_CONTACT_MA) {
        drv8838.brake();
        ground_contact_detected = true;
    }
}

// Phase E: Payload release via servo-actuated hook.
// MAV_CMD_DO_SET_SERVO sends a PWM command to Pixhawk auxiliary servo output.
// Pixhawk routes this to the release servo via its auxiliary PWM channel.
// Wait 500ms, then confirm the current has dropped (confirming load is gone).
mavsdk.send_command(MAV_CMD_DO_SET_SERVO, servo_channel, RELEASE_PWM);
std::this_thread::sleep_for(500ms);
confirm_current_drop(drv8838);   // Current back to idle = payload detached.

// Phase F: Soft ramp reel-back.
// Same ramp logic as lowering, but at 20% duty in reverse.
// Without payload, the free cable swings MORE (no damping mass),
// so the wobble guard remains active throughout reel-back.
ramp_drv8838(from=0.0f, to=-WINCH_RETRACT_DUTY, steps=RAMP_STEPS, interval_ms=RAMP_INTERVAL_MS);
// ... (same swing-damp loop as Phase C, active during reel-back)

// Phase G: Spool home detection.
// Hall effect sensor on spool axle fires when the spool returns to home position.
// Alternative: N20 back-EMF drops when motor can no longer turn (spool bottomed out).
// Either signal → brake and disarm winch.
wait_for_spool_home(hall_sensor, back_emf_monitor);
drv8838.brake();
winch_armed = false;
What is the DRV8838? Can it handle the current?
The DRV8838 is a single H-bridge motor driver IC from Pololu. It can handle up to 1.8A peak. The N20 gear motor draws around 50–80mA at normal running speed and spikes to ~180mA at stall — well within the DRV8838's rating. The H-bridge also has built-in current sensing which is how we detect the ground-contact stall without a separate sensor.
What if the payload gets stuck and never reaches the ground?
There's a maximum lower time timeout. If the ground-contact current threshold hasn't been detected after (cable length / lowering speed + safety margin) seconds, the FSM triggers a brake, logs the anomaly, and either attempts a reel-back or initiates RTL depending on the severity. The 3DR backup telemetry also allows the ground operator to command a manual override.
TOPIC 07

CG Compensation After Payload Drop

When the 100g payload releases, total mass drops by ~5.4% and the centre of gravity shifts. Without correction, the drone would suddenly climb. Three-step compensation: throttle feed-forward reduction, attitude bias injection, then stability gate.

/**
 * CG COMPENSATION — three steps immediately after payload release
 *
 * What happens at the moment of release:
 *   1. Total mass drops from ~1850g to ~1750g (~5.4% reduction)
 *   2. The throttle PID was tuned with the payload attached.
 *      At the same throttle command, the lighter drone climbs.
 *   3. CG shifts slightly upward (and possibly laterally if the
 *      payload was not perfectly centred under the frame).
 *
 * We handle this in three steps:
 *   Step 1: Immediately reduce throttle feed-forward by the mass ratio.
 *   Step 2: Inject a pre-computed attitude bias via MAVLink for 2 seconds
 *           to counteract the CG shift transient.
 *   Step 3: Wait at a stability gate before any dynamic manoeuvres.
 */

// Step 1: Throttle feed-forward reduction.
// The feed-forward is the "baseline" throttle that balances gravity
// before the PID error terms kick in. It scales linearly with mass.
const float PAYLOAD_MASS_KG = 0.100f;
const float DRONE_MASS_KG   = 1.850f;   // total AUW with payload
const float mass_ratio      = PAYLOAD_MASS_KG / DRONE_MASS_KG;  // ~0.054 = 5.4%

float new_throttle_ff = current_throttle_ff * (1.0f - mass_ratio);
send_throttle_feedforward(new_throttle_ff);   // Sent via MAVLink immediately.

// Step 2: Attitude bias injection for 2 seconds.
// cg_pitch_bias_rad and cg_roll_bias_rad are calculated from the
// known mechanical CG offset (measured during assembly) and
// stored as pre-computed constants before the flight.
// The SET_ATTITUDE_TARGET command tells the FC "hold this attitude"
// which counteracts the transient disturbance as the PID re-converges.
AttitudeTarget cg_correction;
cg_correction.pitch = cg_pitch_bias_rad;   // pre-computed from assembly measurement
cg_correction.roll  = cg_roll_bias_rad;
mavsdk.set_attitude_target(cg_correction);
std::this_thread::sleep_for(2000ms);   // Hold for 2s then Pixhawk PID takes over.

// Step 3: Stability gate — must pass BEFORE any dynamic manoeuvres.
// This confirms the Pixhawk EKF3 and attitude PID have re-converged
// to the new lighter equilibrium. Prevents the return flight starting
// while the drone is still oscillating from the mass change.
auto wait_for_cg_settle = [&]() {
    auto t_start = now();
    while (elapsed(t_start) < 5.0f /* 5s timeout */) {
        float roll_rate  = std::fabsf(telem.roll_rate_dps());
        float pitch_rate = std::fabsf(telem.pitch_rate_dps());
        float gps_speed  = std::hypotf(telem.vel_north(), telem.vel_east());

        if (roll_rate < 3.0f && pitch_rate < 3.0f && gps_speed < 0.5f)
            return STABLE;   // Gate passed — safe to start return flight.

        std::this_thread::sleep_for(50ms);
    }
    return TIMEOUT;   // 5s elapsed — proceed anyway, log the event.
};
TOPIC 08

Auto Brightness Normalisation (CLAHE)

The drone transitions from a shaded corridor to open sunlight. Without correction, the YOLO model and HSV red/green masks fail on over-exposed frames. CLAHE is applied to the L-channel of LAB colour space — correcting brightness locally without touching hue.

/**
 * AUTO BRIGHTNESS NORMALISATION — CLAHE on LAB L-channel
 *
 * Problem: OAK-D Lite transitions from dark corridor to bright sunlight.
 *   In shade: frame is underexposed → low contrast → YOLO misses detections.
 *   In sun:   frame is overexposed  → colours wash out → HSV mask fails.
 *
 * Why not just use auto-exposure on the camera?
 *   Camera AE takes ~500ms to settle after large light changes.
 *   We can't wait 500ms — that's 15 FSM cycles. We need every frame usable.
 *
 * Why CLAHE on LAB L-channel?
 *   LAB colour space separates Lightness (L) from colour (A = green-red axis,
 *   B = blue-yellow axis). CLAHE on L adjusts local brightness/contrast
 *   WITHOUT touching the A or B channels → Hue is preserved for HSV masks.
 *
 *   If we applied CLAHE in BGR or HSV space directly, the colour information
 *   would change, breaking our carefully tuned HSV red/green thresholds.
 *
 * Runs on TX2 NX CUDA BEFORE frame enters Myriad X inference queue.
 */
cv::Mat normalize_frame(const cv::Mat& bgr) {

    // Convert to LAB colour space.
    cv::Mat lab;
    cv::cvtColor(bgr, lab, cv::COLOR_BGR2Lab);

    // Split into 3 channels: L (lightness), A (green-red), B (blue-yellow).
    std::vector<cv::Mat> channels;
    cv::split(lab, channels);

    // Apply CLAHE only to L channel.
    // clipLimit=2.0: limits contrast amplification to prevent noise explosion.
    // tileGridSize=(8,8): local neighbourhood for adaptive histogram equalisation.
    auto clahe = cv::createCLAHE(/*clipLimit=*/2.0, cv::Size(8, 8));
    clahe->apply(channels[0], channels[0]);   // channels[0] = L

    // Merge back and convert to BGR.
    cv::Mat result;
    cv::merge(channels, lab);
    cv::cvtColor(lab, result, cv::COLOR_Lab2BGR);

    // Auto-saturation: if frame is washed out (mean saturation < 60),
    // scale the S channel up to restore colour discriminability.
    // Cap at 1.5× to avoid artificial over-saturation artefacts.
    cv::Mat hsv;
    cv::cvtColor(result, hsv, cv::COLOR_BGR2HSV);
    cv::split(hsv, channels);
    float mean_sat = cv::mean(channels[1])[0];
    if (mean_sat < 60.0f) {
        float scale = std::min(1.5f, 80.0f / mean_sat);
        channels[1].convertTo(channels[1], -1, scale, 0);
    }
    cv::merge(channels, hsv);
    cv::cvtColor(hsv, result, cv::COLOR_HSV2BGR);
    return result;
}

Emergency Override & RTL

Important: the Pixhawk has INDEPENDENT RTL authority. Even if the TX2 NX crashes or stops responding, the Pixhawk's own failsafes (battery, GPS, geofence, datalink) trigger RTL by themselves. The TX2 NX adds software-level triggers ON TOP of the hardware failsafes — it does not replace them.

What is the role of the 3DR radio in safety?
The 3DR 915MHz radio is a secondary independent MAVLink link between the drone and ground station. Its two roles: (1) offboard compute relay for A-star on the return lap, and (2) payload safety monitoring — the GCS gets real-time winch state, current readings, and release confirmation. If the Skydroid T12 primary RC link drops during delivery, the ground operator can command RTL over the 3DR link without needing the TX2 NX to be responsive.
